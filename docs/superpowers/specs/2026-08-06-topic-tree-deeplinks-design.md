# Topic Tree Canvas & Zotero Deep Links — Design Spec

- **Date:** 2026-08-06
- **Status:** User-approved architecture, pending written-spec review
- **Targets:** `src/lib/knowledge` (validator/projection), `knowledge/index.qmd`,
  `skills/`, `integrations/zotero` (site-browser link interception)
- **Related spec:**
  [`2026-08-06-workbench-tabs-design.md`](./2026-08-06-workbench-tabs-design.md)
  (phase A; this document covers phases B and C of the same effort)

## Overview

Two features share one trust-boundary decision and land together:

- **Deep links (C):** knowledge and draft QMD pages may link straight into
  Zotero — `zotero://open-pdf/library/items/KEY?page=N` opens the PDF at that
  page. The knowledge validator, which today hard-fails every non-http scheme,
  learns to admit exactly the `zotero:` scheme.
- **Topic tree canvas (B):** `knowledge/index.qmd` renders an interactive,
  draggable tree of topics. Hovering a node shows two links — open the PDF in
  Zotero, open the QMD note on the site — each greyed out when absent. The
  tree is defined by a YAML block in `index.qmd`; the interactive layer is
  generated by the build, never authored in page content.

An AI skill (`skills/edit-topic-tree/`) teaches agents to edit the tree block
correctly.

## Trust-boundary decisions (user-approved)

1. **`zotero:` joins the external-scheme allowlist.** The parser's external
   target test widens from `/^(?:https?|mailto):/i` to
   `/^(?:https?|mailto|zotero):/i` (`src/lib/knowledge/parser.ts:68`).
   `zotero:` links are treated exactly like https — passed through unvalidated
   in shape, excluded from tree-internal resolution. Every other scheme
   (`javascript:` included) keeps hard-failing with `LINK_OUTSIDE_KNOWLEDGE`.
2. **Interactive JS enters through the projection, not through pages.** Pages
   still may not contain `<script>` (the `SCRIPT_FORBIDDEN` gate is
   untouched). The tree runtime ships as a build-generated asset injected via
   the *generated* `_quarto.yml` — the same trusted channel that already
   generates `research-loop.css`.

## Deep links (C)

**Authoring forms** (documented in the skill):

- Open a PDF at a page: `[Kitaev 2003, p.12](zotero://open-pdf/library/items/ITEMKEY?page=12)`
- Select an item: `zotero://select/library/items/ITEMKEY`
- Group libraries: `zotero://open-pdf/groups/<groupID>/items/KEY?page=N`

**Click behavior:**

- **External browsers:** the OS `zotero:` protocol handler opens desktop
  Zotero at the page. No code.
- **The workbench's embedded site browser:** `ResearchLoopSiteView`
  (`integrations/zotero/src/research-loop-site.ts`) attaches a progress
  listener that cancels `zotero:` navigations and handles them natively —
  preferring the existing `focusWorkbenchPdfTab` (jump an already-open
  workbench PDF tab to the page), else `Zotero.Reader.open(item,
  { pageIndex })`. If the remote-browser cancel proves unavailable in live
  Zotero, the fallback is to let the OS handler take it (an extra system
  prompt, no lost function) — same strategy-chain-plus-live-QA treatment as
  the embedded reader spike.

`drafts/` renders are link-unvalidated already and need no change.

## Tree definition block (B)

Allowed only in `knowledge/index.qmd`, as an ordinary fenced code block
(current validation admits its contents untouched):

````markdown
```qlab-tree
root: Research Knowledge
nodes:
  - label: Tensor Networks
    note: TN_sim/index.qmd        # optional; missing → grey note link
    zotero: zotero://select/library/collections/ABCD1234  # optional; missing → grey PDF link
    x: 120                        # optional canvas coords; "Copy layout" fills them
    y: 80
    children:
      - label: MPS & DMRG
        note: TN_sim/MPS_DMRG.qmd
        zotero: zotero://open-pdf/library/items/KEY?page=4
```
````

**New build module `src/lib/knowledge/tree.ts`** (uses the repo's existing
`yaml` dependency):

- Extracts the `qlab-tree` block from the index page source and parses it.
- Validation joins the `make knowledge-check` diagnostics: non-empty `label`,
  unique among siblings; `note`, when present, must resolve to a real page via
  `resolveTarget` (else new code `TREE_NOTE_MISSING`); `zotero`, when present,
  must start with `zotero://` (else `TREE_LINK_SCHEME`); `x`/`y` must be
  numbers; a `qlab-tree` block on any page other than the root index is a
  diagnostic.
- Compiles to canonical JSON; node ids derive stably from the label path, and
  each `note` is emitted as its resolved site URL (`/knowledge/<page>.html`)
  so the runtime never re-derives paths.

**Projection injection** (`src/lib/knowledge/quarto.ts`, same trusted channel
as the generated CSS):

- Generates `research-loop-tree.js` = a dependency-free ES-module runtime
  (a static file in the repo, copied byte-for-byte) plus the compiled JSON.
- `FIXED_BASE_CONFIG` gains an `include-in-header` that loads the script with
  `defer`; the committed `knowledge/_quarto.yml` receives the identical
  addition so the strict-equality assertion (`assertSafeBaseConfig`) holds.
- Generated CSS hides the raw `qlab-tree` code block on the rendered page;
  the runtime mounts the SVG canvas in its place. On pages without a tree
  block the runtime exits silently.

Bad data fails the build with line-numbered diagnostics; browsers only ever
see a valid tree.

## Canvas runtime (B)

Hand-written SVG, no dependencies, ~300 lines:

- **Layout:** nodes without coordinates get a tidy-tree automatic layout;
  authored `x`/`y` win. Effective position priority: localStorage > authored
  `x`/`y` > automatic.
- **Interaction:** drag the background to pan, wheel to zoom, pointer-drag
  nodes; positions persist to `localStorage` per browser.
- **Hover card:** hovering a node (tap on touch) floats a card with the node
  label and two links — "Open PDF in Zotero" (`zotero` field) and "Open note"
  (site URL of the note page) — each rendered grey and inert when its field
  is absent.
- **Tool corner:** "Copy layout YAML" merges current positions back into the
  block content and copies it to the clipboard (paste into `index.qmd`, or
  hand to the AI, to freeze the layout); "Reset layout" clears localStorage.
- Light/dark follows the generated theme's CSS variables.

**Editing model:** node content and edges are edited in `index.qmd` (workbench
editor or any editor); the per-document Quarto preview re-renders on save —
that is the "preview editing" path. Canvas dragging is presentation-layer
only.

**Initial content:** the first `qlab-tree` block is generated from the current
Reading map's 20 topics — `note` pointing at each topic index, `zotero`
filled from the existing `literature/zotero.yml` collection mapping where one
exists (grey otherwise).

## AI skill

`skills/edit-topic-tree/SKILL.md`, in the repo's two-key frontmatter format:
when to use (user asks to change the topic tree / node links), the full block
schema, both `zotero://` link forms, and the editing rules — English labels;
`note` either resolves to an existing page or is omitted; always run
`make knowledge-check` after edits; preview with `make knowledge-preview`;
the tree is a presentation layer and the Reading map remains the navigation
authority. A matching entry joins
`.research-loop/tests/agent/skill-contracts.test.ts`.

## Error handling

- Malformed YAML, missing note targets, bad schemes, misplaced blocks →
  build-time diagnostics via `knowledge-check`; the site never renders a
  broken tree.
- Runtime: absent tree block → no-op; localStorage unavailable → in-memory
  positions for the session; clipboard API unavailable → the "Copy layout"
  button shows the serialized YAML in a selectable block instead.
- In-plugin interception failure (live-QA finding) → OS protocol handler
  fallback, recorded in the QA checklist.

## Testing

- `tree.test.ts` — block extraction, YAML parsing, every diagnostic path,
  deterministic JSON compilation.
- Projection tests — asset + header injection emitted; `_quarto.yml`
  equality assertion updated; no canvas artifacts when the index has no tree
  block.
- Runtime pure-function tests (vitest imports the ES module) — automatic
  layout, position-priority merge, "Copy layout" YAML round-trip.
- Parser tests — `zotero:` passes, `javascript:` still fails.
- Plugin tests — site-browser interception with a fake browser; live behavior
  joins the existing live-Zotero QA checklist.

## Implementation deviations (recorded post-implementation)

1. **Layout serialization regenerates the block.** The browser runtime only
   has the compiled JSON (the authored YAML is not shipped), so "Copy layout
   YAML" re-emits the whole block from the compiled tree
   (`serializeTreeYaml`) instead of merging coordinates into the original
   text. Comments inside the block therefore do not survive a freeze.
2. **`resources` in the generated config.** Quarto copies a root-level
   script into the site only when it is a declared resource; the *generated*
   `_quarto.yml` names exactly `research-loop-tree.js` (the committed base
   file still may not mention resources), and the projection safety pin now
   asserts that single fixed entry rather than forbidding the key.

## Non-goals

- No editing or write-back from the canvas itself; no server-side write path.
- No shape validation of `zotero://` URLs beyond the scheme (https links are
  not shape-checked either).
- No OJS, no client-side YAML parsing, no charting/diagram libraries.
- The Reading map's authority over site navigation and graph curation is
  unchanged.
